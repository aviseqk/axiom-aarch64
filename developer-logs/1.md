> *[LOG-001] · 03-09-2026 · Planning · Decision · Processor Boot Ownership · DECIDED*

# for the hypervisor vision, the idea was to trust QEMU's firmware/boot mechanism to hand us over code control at EL2 step and from there Axiom would take over, making Axiom the EL2 component for the execution environment. This could have been done
# by using TF-A as the intermediary step and TF-A's BL1 would do the EL3 init then transition to EL2 and then Axiom could have taken over from there.

# or the other way would be, that instead of letting QEMU firmware hand us EL2, we could have our own, Axiom's own EL3 boot firmware, where Axiom directly takes control from the processor reset and the flow is like
## Processor RESET -> Axiom EL3 -> Axiom EL2 -> Axiom EL3 Monitor -> Axiom EL2 Hypervisor -> Guest EL1      (eventually, very similar to what TF-A does, but the whole processor boot will be in our control)

## Since, the goal of this project was to completely own the execution environment, from the most bare-metal-ish entrypoint (EL3 firmware), hence I have decided on taking the latter direction.
## We will need to provide firmware code that exists at the CPU's reset location, so that Axiom itself could start at EL3.

> *[LOG-002] · 03-09-2026 · Boot/Reset · Question · Platform and Initial State · OPEN · FOLLOWS: [LOG-001]*

- A lot of questions arise when we choose the manual loading path of the qemu machine, both related to the machine in question, (qemu's virt) and also the processor in work. Initially, While planning development, I wondered about the following:
1. We would need to understand the QEMU's boot mechanism right, before writing our first line of code of Axiom. Questions like, 
        a.) What exactly does QEMU prepare before it invocates when it is creating its machine, and before our piece of code?
        b.) Where does QEMU put our firmware code?
        c.) What address does the virtual CPU of QEMU execute just after reset?  these addresses would be required for our linker script later.

2. Before writing our linker script, we would need to know all the platform-specific arrangements made by QEMU.
3. The general approach of using QEMU is to either provide TF-A as the firmware or let QEMU's firmware decide, but what happens when QEMU is provided no firmware?
4. Can we say with full confidence, that post QEMU hands us, and when the execution starts, the CPU starts at the EL3 exception level?

## NOTE: Once we have the above questions figured out, we can safely start referencing ARM ARM and its processor architecture state to start the first initial assembly.
